# dom-locators

Vitest browser mode's `page` and its locators, with their waiting and their actions, answered inside the document under test: no selector engine of the provider, no round trip to it, no Testing Library.

A test of `vitest/browser` changes one import:

```diff
- import { page } from "vitest/browser";
+ import { page } from "dom-locators";

  await page.getByLabelText("Title").fill("Groceries");
  await page.getByRole("button", { name: "Create note" }).click();
  await expect.element(page.getByText("Note created.")).toBeInTheDocument();
```

A private package of this repository, for its playgrounds and its benchmark: not on npm.

## The contract

For every locator it accepts, `dom-locators` returns the elements that Vitest's `page` returns, in the same order. A locator, an option or a method it does not model throws `UnsupportedError` with the reason; an invalid value of an option it does model throws a `TypeError`. It never returns another element.

One exception, of a locator of an element: `elementLocator(element)` and `all()` hold the element itself, and print it as Vitest's CSS path of it. Vitest's, with Playwright, prints a selector that Playwright generates for it, and finds by that selector again at each look: a node that React replaces is a new one to Vitest's and gone to the package's, and the `selector`, the `asLocator()` and the first line of an error of such a locator are others.

The roles, the ARIA states, the accessible names and the text matching are Playwright's, ported from the engine Vitest 5's locators run (ivya 1.8.2, Playwright at 4554372e, see [NOTICE](NOTICE)). The package's own suite holds every locator of a table, on an ARIA page and on the routes of the notes app, to `vitest/browser`'s `page`: the same elements, the same `selector`, the same `asLocator()`.

Open shadow roots are looked into, as Vitest's locators do and in their order: a tree's elements, then the trees of its shadow roots, each host's in the order of the document. A closed shadow root is nobody's: neither finds what is in it. Next's `<next-route-announcer>`, on every page of the App Router, has an open one.

Vitest's defaults apply: `exact` is Vitest's `browser.locators.exact` (`true` unless your config says otherwise) and `getByTestId()` reads `browser.locators.testIdAttribute`.

## What there is

- `page`: `getByRole`, `getByText`, `getByLabelText`, `getByPlaceholder`, `getByAltText`, `getByTitle`, `getByTestId`, `elementLocator(element)`, `extend(methods)`.
- A locator: the same `getBy*`, `filter({ hasText, hasNotText, has, hasNot })`, `nth`, `first`, `last`, `and`, `or`, `all`, `element`, `elements`, `query`, `length`, `findElement({ timeout, strict })`, `selector`, `toString`, `asLocator`, `serialize`, `toJSON`.
- Actions: `click`, `dblClick`, `tripleClick`, `hover`, `unhover`, `fill`, `clear`, `selectOptions`, `upload` of `File`s, `wheel`, `dropTo` of what the page drags with the mouse's events, and two that Vitest's `Locator` does not have, Playwright's `press(key)` and `pressSequentially(text)`. `press` takes `"Enter"`, `"Escape"`, `"Tab"`, `"Backspace"`, `"Delete"`, `"Space"` or `" "`, the arrows, `"Home"`, `"End"`, a modifier or one printable character, after the modifiers held for it: `"Shift+Tab"`, `"ControlOrMeta+a"`.
- The options of an action are Playwright's that the page can model: `timeout` for every one, where 0 is no limit, as Playwright's; `force` for the clicks, `hover`, `unhover`, `fill`, `clear`, `selectOptions` and `dropTo`; `noWaitAfter` (no effect, as in Playwright) for those and `upload`, `press` and `pressSequentially`; `modifiers`, `position` and `trial` for the mouse's, `sourcePosition`, `targetPosition` and `trial` for `dropTo`; `button` for the clicks; `clickCount` for `click`. Any other option throws, and so does an invalid value. With `force` an action does not wait: it acts on an element that is visible, enabled and, for typing, editable, and throws for one that is not, where Playwright's would act on it and the browser's answer is not the page's.
- `configure({ testIdAttribute, timeout })`, and `UnsupportedError`.

Without Browser Mode, in a DOM of Node.js, Vitest has no `expect.element()`: a setup file that imports `dom-locators/expect-element` adds one of the same shape, which waits with `findElement()`, with the matchers of a DOM library, like `@testing-library/jest-dom/vitest`.

`expect.element(locator)` takes a locator of the package, with `.not`, `toHaveLength` and `{ timeout }`: it carries Vitest's locator symbol and has the methods `expect.element` calls. A locator is assignable to `Locator` of `vitest/browser`.

Not yet, on the type and throwing with the way out, `vitestPage.elementLocator(await locator.findElement())`: `screenshot`, `mark`, `page.viewport`, `page.screenshot`, `page.mark`, `page.frameLocator`. A locator of `vitest/browser` in `filter({ has })`, `and` or `or` throws too, and so do `upload` of a path, which the page cannot read, and `dropTo` of an element the browser drags itself, `draggable` as a link or an image is: Chrome's drag and drop of HTML.

## Waiting

One look now, one after each batch of changes of the DOM (one `MutationObserver` for the whole wait), one every 50 ms besides, until the deadline: the caller's `timeout`, else the running test's time left (minus Vitest's margin, so the locator is in the error), else `configure({ timeout })`, 1000 ms by default. `findElement()` and every action wait so; `expect.element()` waits through `findElement()`. The test's fake timers do not stop it.

An action waits for one element and that it is visible: `click`, `dblClick`, `tripleClick`, `hover`, `fill`, `clear`, `selectOptions`, `wheel` and `dropTo`. The clicks, `fill`, `clear` and `selectOptions` also wait for it to be enabled, and `fill` and `clear` editable, as Playwright's: of the button, checkbox or radio it is in, else of the control of its label. `press`, `pressSequentially` and `upload` wait for the element alone, and `unhover`, as Vitest's, for none. A disabled button is not clicked: the action fails after its timeout, naming the locator and what it waited for.

## In a DOM of Node.js

The package runs in happy-dom and in jsdom too, as Vitest's `environment`: the package's suite holds its locators there to ivya, the engine of Vitest's locators, in the same DOM, its actions to Playwright's events in Chromium, step by step, recorded by the browser's fidelity test, and its waits to their tests. What the DOM itself does otherwise is the DOM's: the click of a label on its control, happy-dom's `data` of an `InputEvent` and its `focus()` of any element, jsdom's `select` of every caret that moves. Such a DOM lays nothing out and draws nothing, and the package answers so:

- An element is visible by its style alone: no `display: none` on it or above it, and no `visibility: hidden`; a style without a visibility, happy-dom's, is visible.
- A click lands on the element itself, at 0, 0, as there is no box to hit; `wheel` scrolls nothing.
- Pseudo-elements add nothing to a name, as there are no styles of them.
- Events get no `view`, which the window of Vitest's jsdom environment is not to jsdom's events; a DOM without `PointerEvent` or `InputEvent` gets a `MouseEvent` or an `Event`; `isContentEditable` is read from the attribute where jsdom has none; `upload` throws in jsdom, which has no `DataTransfer`.
- The deadline of a wait is the running test's, from Vitest's worker.

The package knows such a DOM by Node.js running the page and jsdom or happy-dom by its user agent, or an empty root element for another agent; not by the boxes alone, which a test of jsdom may mock, nor by a `process` of Node.js alone, which a polyfill gives a browser's page.

## Speed

On a page of the notes app with 20 notes, on a Mac with Chromium, medians of 5 runs of `test/micro.test.ts`: a link by its name, `getByRole("link", { name })`, with the whole accessible name, in 42 µs, where Vitest's own takes 162 µs; `getByText()` in 40 µs; a `click()`, with the query and the mouse's way to the element, in 61 µs, where Vitest's takes 50 ms; a `fill()` in 26 µs. A change of the DOM before an action adds the style and the layout it then forces, which Playwright forces too. In the notes benchmark, the 500 tests of `tests/dom-locators/` take about 2 ms per test less than the same tests with Testing Library's user-event and Vitest's locators. The micro test prints its numbers (run it with `--reporter=default --silent=false` where Vitest hides a passing test's console) and holds the package's to no more than Vitest's in the same run, as a CI runner's speed is its own.

What makes a query fast, with Playwright's answers: an exact name rules an element out by its own text before the styles of its pseudo-elements are looked up; `checkVisibility()` tells a visible box without the computed style; an exact text is compared by its count of characters that are no white space before it is normalized; and a click needs no hit test for an element with no element in it.

Where the rest goes, in a CPU profile of the benchmark's column (one run, the profiler on): the package takes about 2.4 ms per test, half of it in the browser's own work that it calls. A focus is 0.40 ms: Chrome brings the style up to date and dispatches the blur and the focus. The check that an element is visible is 0.35 ms: the layout and the style it reads, which Playwright's actions force too. The dispatch of the events is 0.2 ms. Its own JavaScript is 1.1 ms, mostly the queries: an action's or a find's first look, and a look after each batch of changes while it waits. Without another answer or another event, about 0.1–0.15 ms per test is left: the init objects of the boundary events on the way of the mouse, and the search for what a press focuses. Looking less often while a wait goes on would save more, but would see the element later.
